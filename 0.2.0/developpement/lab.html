Lab de test multi-nœud#

Ce qui fait l’intérêt de two ne se voit qu’à partir de deux hyperviseurs : sur un nœud isolé, le trafic reste sur le bridge local et l’absence de plan de contrôle passe inaperçue (voir Architecture du cluster). Le lab reproduit la topologie du cluster — hyperviseurs, route reflectors, switchs L3 — sous forme de VM, sur un serveur physique loué à l’heure.

Le pourquoi des choix (serveur physique plutôt que VM cloud, câbles QEMU, MTU 9000, versions) est consigné sur le ticket #50. Cette page décrit comment s’en servir.

Note

État actuel : le lab de #50 est livré et l’outil en est sorti (#55) : c’est labctl, un dépôt à part, dont two épingle une release. Ce dépôt garde ce qui est propre à two — ses topologies, l’installation de two sur les hyperviseurs, les scénarios et leurs résultats. La redondance du plan de contrôle — deux route reflectors, deux switchs en VRRP v3 — est livrée par #54 (fermé), et qualifiée par les tests 71 et 72.

L’outil#

labctl monte un lab de VM QEMU à partir d’une topologie YAML et s’exécute sur un hôte Linux avec KVM ; son lab-host.sh loue cet hôte à l’heure chez Scaleway (Elastic Metal), le prépare, y dépose labctl et la topologie, puis le supprime. Prérequis Scaleway, fichiers locaux (~/.config/labctl/), commandes, format de topologie, rendu des VM, garanties de facturation et diagnostic : voir le guide de labctl.

two n’en garde aucune copie. test/e2e/labctl.sh épingle une release :

  • au premier appel, il télécharge labctl_linux_amd64 et lab-host.sh dans ~/.cache/labctl/release/<version>/ et les vérifie contre des sommes SHA-256 écrites dans le script — une release modifiée après coup est refusée ; un fichier altéré dans le cache est retéléchargé ;

  • il lance ensuite lab-host.sh avec ses arguments et LABCTL_BIN pointé sur le binaire : push dépose ce binaire au lieu de compiler.

Changer de version : LABCTL_VERSION et les deux lignes de LABCTL_SUMS dans test/e2e/labctl.sh, relevées dans le SHA256SUMS de la release et recalculées sur les fichiers téléchargés.

Une campagne, depuis le Mac :

test/e2e/labctl.sh plan                                   # gratuit : offre, zone, prix
test/e2e/labctl.sh up                                     # crée le serveur, facturé à l'heure
test/e2e/labctl.sh push test/e2e/topologies/evpn-3hv.yml
test/e2e/labctl.sh ssh './labctl up -timeout 25m topology/evpn-3hv.yml'
test/e2e/run.sh all
test/e2e/labctl.sh ssh './labctl ssh hv1'                 # shell interactif sur hv1
test/e2e/labctl.sh down                                   # supprime le serveur

Avertissement

Un serveur Elastic Metal est facturé de sa création à sa suppression, chaque heure entamée comme une heure pleine. En cas de doute (session interrompue, poste mis en veille) : test/e2e/labctl.sh status puis down. Ne jamais lancer lab-host.sh sous bash -x : la trace afficherait la clé d’API.

Topologies#

Les topologies de two vivent dans test/e2e/topologies/ : evpn-2hv.yml (deux hyperviseurs) et evpn-3hv.yml (trois, celle de la suite). Le format est celui de labctl :

name: evpn-2hv

images:
  debian12:
    url: https://cloud.debian.org/images/cloud/bookworm/latest/debian-12-generic-amd64.qcow2
    sums: https://cloud.debian.org/images/cloud/bookworm/latest/SHA512SUMS

segments:
  underlay:
    routers: [sw1, sw2]
    cidr: 192.168.14.0/24
    mtu: 9000
  lan:
    cidr: 10.33.0.0/24
    mtu: 1500

nodes:
  sw1:
    { role: router, image: debian12, cpus: 2, memory: 1024, segments: [underlay],
      addresses: { underlay: 192.168.14.2 }, secondary: { underlay: [169.254.0.1/28] },
      frr: frr/sw1.conf }
  sw2:
    { role: router, image: debian12, cpus: 2, memory: 1024, segments: [underlay],
      addresses: { underlay: 192.168.14.3 }, secondary: { underlay: [169.254.0.2/28] },
      frr: frr/sw2.conf }
  rr1:
    { role: rr, image: debian12, cpus: 1, memory: 1024, segments: [underlay],
      addresses: { underlay: 192.168.14.4 }, secondary: { underlay: [169.254.0.3/28] },
      loopback: 10.255.255.1/32, frr: frr/rr1.conf }
  rr2:
    { role: rr, image: debian12, cpus: 1, memory: 1024, segments: [underlay],
      addresses: { underlay: 192.168.14.5 }, secondary: { underlay: [169.254.0.4/28] },
      loopback: 10.255.255.2/32, frr: frr/rr2.conf }
  hv1:
    { role: host, image: debian12, cpus: 4, memory: 16384,
      segments: [underlay, lan], addresses: { underlay: 192.168.14.11, lan: 10.33.0.11 },
      frr: frr/hv1.conf, provision: provision/hypervisor.sh,
      post_provision: provision/hypervisor-post.sh, files: { agent.yml: agent/two.yml, bin: bin },
      services: [agent.service] }
  hv2:
    { role: host, image: debian12, cpus: 4, memory: 16384,
      segments: [underlay, lan], addresses: { underlay: 192.168.14.12, lan: 10.33.0.12 },
      frr: frr/hv2.conf, provision: provision/hypervisor.sh,
      post_provision: provision/hypervisor-post.sh, files: { agent.yml: agent/dnsmasq.yml, bin: bin },
      services: [agent.service] }

Les ASN, les loopbacks des route reflectors, le lien 169.254.0.0/28 et le subnet des hyperviseurs de l’exemple sont ceux de la production (décision du 2026-10-04, #50) : les fichiers de test/e2e/topologies/ restent ainsi au plus près de ce qui tourne réellement. Toutes les adresses y sont fixées par addresses — les switchs en .2 et .3, les route reflectors en .4 et .5, les hyperviseurs à partir de .11 — pour que le modèle se lise sans le plan et ne dépende pas de l’ordre de déclaration : le frr.conf d’un hyperviseur, écrit à la main, porte son adresse en router-id. Les deux switchs sw1 et sw2 sont les routeurs du segment (rôle router de labctl) : la passerelle, la première adresse du segment, est portée en VRRP v3 par celui qui est maître, sans préemption (no vrrp 1 preempt) — voir la section du guide de labctl sur les routeurs. Leurs frr.conf ne diffèrent que par hostname et router-id ; labctl y ajoute la strophe VRRP.

Rôles#

Les configurations FRR du lab vivent dans test/e2e/topologies/frr/, une par nœud, écrites à la main : ce sont les mêmes fichiers que la documentation de déploiement inclut, pour que le lab qualifie exactement ce qu’elle prescrit. Celles des hyperviseurs se réduisent à hostname et log : la configuration BGP est posée par l’agent (section bgp de agent.yml). Celle du premier route reflector (celle de rr2 ne diffère que par son nom et sa loopback) :

frr defaults traditional
hostname rr1
log syslog informational
!
ip prefix-list RR-LOOPBACK-OUT seq 10 permit 10.255.255.1/32
!
route-map NO-IN deny 999
 description deny
exit
!
router bgp 65000
 no bgp default ipv4-unicast
 bgp router-id 10.255.255.1
 bgp cluster-id 10.255.255.1
 neighbor CLUSTER peer-group
 neighbor CLUSTER remote-as 65100
 neighbor CLUSTER bfd
 neighbor 169.254.0.1 peer-group CLUSTER
 neighbor 169.254.0.1 description router-1
 neighbor 169.254.0.2 peer-group CLUSTER
 neighbor 169.254.0.2 description router-2
 neighbor fabric peer-group
 neighbor fabric remote-as 64600
 neighbor fabric local-as 64600 no-prepend replace-as
 neighbor fabric capability extended-nexthop
 neighbor fabric update-source 10.255.255.1
 bgp listen range 192.168.14.0/24 peer-group fabric
 bgp listen limit 200
 !
 address-family ipv4 unicast
  network 10.255.255.1/32
  neighbor CLUSTER activate
  neighbor CLUSTER prefix-list RR-LOOPBACK-OUT out
  neighbor CLUSTER route-map NO-IN in
 exit-address-family
 !
 address-family l2vpn evpn
  neighbor fabric activate
  neighbor fabric route-reflector-client
 exit-address-family
 !
exit
!

FRR est installé par labctl au premier démarrage (frr-stable de deb.frrouting.org, clé du dépôt embarquée dans l’outil) : voir la section FRR du guide de labctl.

Hyperviseurs. Ce sont des nœuds host dont la provision installe two comme en production. test/e2e/topologies/provision/hypervisor.sh dépose agent.yml (fichier agent.yml du nœud) dans /etc/two/agent.yml, télécharge deploy.sh et bootstrap_kvm.sh au tag de la release testée dans /opt/two/scripts/, où deploy.sh cherche d’abord bootstrap_kvm.sh, puis lance :

deploy.sh --noup_script -i -u "$LAB_UPLINK" -t <release>

La release est fixée dans le script (RELEASE=) : sans elle, deploy.sh prendrait la dernière, et le lab ne serait plus reproductible. --noup_script empêche l’auto-mise à jour de remplacer le script par celui de main. L’uplink -u est l’interface qui porte la route par défaut, parce que deploy.sh y lit l’adresse et la passerelle qu’il déplace sur br-000000. deploy.sh télécharge la release sur git.g3e.fr sans réessayer : le script attend d’abord que le serveur réponde, à travers le switch. Les deux fichiers agent/ donnent à l’agent la section bgp (AS 64600, route reflectors 10.255.255.1 et 10.255.255.2) et un watchdog toutes les 10 s ; agent/two.yml met en plus hv1 sur le serveur DHCP intégré (dhcp.backend: two), agent/dnsmasq.yml met explicitement les autres sur dnsmasq (dhcp.backend: dnsmasq).

Segment ``lan`` (mode ``bridge``). hv1 et hv2 sont aussi reliés à un second segment, lan (10.33.0.0/24, MTU 1500, sans routeur : L2 pur, sans passerelle ni NAT), déclaré après underlay pour ne changer ni ses adresses ni ses taps. Avant deploy.sh, hypervisor.sh crée le bridge br-lan (STP coupé, MTU de l’interface), y rattache l’interface lan et y déplace l’adresse que labctl lui a donnée (10.33.0.11 sur hv1, 10.33.0.12 sur hv2). Les deux fichiers agent/ déclarent interfaces: {lan: br-lan} : un subnet créé avec mode: bridge et iface_type: lan rattache son veth à br-lan. Les subnets vxlan (iface_type: vms, clé absente) restent sur default_interface : le VTEP ne change pas. Le bridge n’est créé qu’au premier démarrage, comme le reste du provisionnement.

Tester l’arbre courant plutôt que la release. test/e2e/build.sh compile agent, dhcp et metadata pour linux/amd64 dans test/e2e/topologies/bin/ (ignoré par git), que les hyperviseurs reçoivent par files: {bin: bin}. Après deploy.sh, hypervisor.sh installe chaque binaire présent dans /opt/two/local/bin/ et y fait pointer /opt/two/bin/<nom> ; le reste (units, scripts) vient de la release. build.sh --clean vide le répertoire : le lab suivant teste la release seule.

test/e2e/build.sh                                   # binaires de l'arbre courant
test/e2e/labctl.sh push test/e2e/topologies/evpn-3hv.yml
test/e2e/labctl.sh ssh './labctl up topology/evpn-3hv.yml'
test/e2e/build.sh --clean                           # retour à la release seule

FRR est installé après la provision : il démarre sur le réseau final. Démarré avant la migration, zebra peut perdre la route par défaut quand elle passe de l’uplink à br-000000 — constaté le 2026-10-11 sur un hyperviseur sur deux : route reflector unresolved, session BGP jamais établie. L’agent, configuré avec une section bgp, refuse de démarrer tant que FRR n’est pas là : son premier démarrage par deploy.sh échoue, et provision/hypervisor-post.sh (post_provision) le redémarre une fois FRR installé.

Avertissement

Un hyperviseur du lab ne survit pas à un redémarrage. En production, la racine est en tmpfs et deploy.sh --bootstrap est rejoué à chaque démarrage ; dans le lab, -i n’est exécuté qu’au premier, et la migration réseau, qui n’est pas persistée, est perdue. Recréer le lab : labctl down puis labctl up.

Vérifié le 2026-10-04 sur le serveur de lab, topologie evpn-2hv, release 0.2.0rc002 :

Note

Les switchs du lab sont des routeurs Linux avec FRR, par choix. Ils jouent le rôle générique de routeur de cluster : passerelle des hyperviseurs, sessions eBGP avec BFD vers les route reflectors, dont ils n’acceptent que les loopbacks (test/e2e/topologies/frr/sw1.conf). L’équipement réel dépend de qui déploie l’infrastructure (MikroTik aujourd’hui ; Cisco, Juniper, Arista… demain) : il n’a besoin que de BGP et d’EVPN, et sa configuration propre au constructeur n’a pas sa place dans le lab.

Suite de tests#

La suite (#70) vit dans test/e2e/suite/ : un fichier par fonctionnalité, rangés en couches de bas en haut. Chaque couche ne s’appuie que sur les précédentes, et les tests de panne passent en dernier. Elle remplace les scénarios s1 à s11, écrits au fil des tickets : chacune de leurs 251 vérifications est reprise (tableau de correspondance sur #70).

Les tests se lancent depuis le Mac, sur un lab démarré (up, push, ./labctl up) :

test/e2e/run.sh all              # toute la suite, dans l'ordre
test/e2e/run.sh 40               # une couche
test/e2e/run.sh 41 dhcp-two      # des tests, par numéro à deux chiffres ou par nom exact
test/e2e/run.sh --from 30        # à partir d'un numéro
test/e2e/run.sh --continue all   # sans s'arrêter sur une couche en échec
test/e2e/run.sh --connus all     # les échecs connus comptent comme des échecs
test/e2e/run.sh --matrice        # matrice de couverture, tirée des en-têtes

Chaque test affiche une ligne RÉUSSI ou ÉCHOUÉ par vérification (un échec porte la dernière ligne de la commande en cause), des lignes INFO pour les mesures, puis son bilan. Le code de sortie vaut 1 si une vérification échoue ou si aucune n’a été faite. Avec all ou --from, une couche en échec arrête la suite à la fin de la couche.

Tests autonomes. Avant chaque test, le runner supprime les ressources tNN laissées par un passage précédent, puis relève l’état de chaque hôte de l’en-tête # hôtes:. Après le test, il supprime ses VM, ses subnets puis ses VPC, et vérifie que l’hôte est revenu à l’état relevé (assert_clean : netns, liens, adresses, routes, règles ebtables et iptables, configuration FRR et frr.conf, fichiers de /run/two, dnsmasq.d et des volumes, unités two-vm-*, processus dnsmasq et QEMU). Aucun test ne dépend d’un autre : n’importe lequel se lance seul.

Plages. Le test NN nomme ses ressources vp-tNN*, sn-tNN* et tNN-*, et utilise 10.NN.0.0/16 et les VNI NN00 à NN99 : aucune collision entre tests.

Échecs connus. Un contrôle dont l’échec est connu et rattaché à un ticket s’écrit known "#NN" "description" commande… au lieu de check. En échec, il sort en CONNU sans faire échouer le test (bilan : N connu(s)). Dès qu’il passe, il sort en INATTENDU et fait échouer le test : le marqueur est à retirer. Pour un échec intermittent, known_flaky sort en RÉUSSI (annoté) quand l’échec ne se reproduit pas, sans rappel automatique : le retrait se fait en fermant le ticket. Chaque ticket concerné liste ses marqueurs en commentaire.

Campagne du 2026-10-17#

Première campagne de la suite, evpn-3hv.yml, labctl 0.2.0, binaires de l’arbre courant (code de l’agent identique à main). run.sh --continue all en 76 min, dont environ 15 min d’arrêts de VM à 300 s et 15 min d’attentes sur des tests en échec. Les hypothèses fausses des tests ont été corrigées sur le serveur et les tests concernés rejoués. Il reste :

  • tout vert, sauf les échecs réels, marqués known et rattachés à leur ticket : multi-NIC (#73, #62), noms des disques SCSI (#74), mode bridge sur plusieurs hôtes (#75), filtrage au port (#76), socket DHCP (#77), fausse alerte du watchdog (#78) ;

  • #69 vérifié : au retour de sw1 (priorité 200), il redevient maître, seconde bascule en 1,2 s, sessions EVPN jamais coupées. La préemption est pourtant désactivée dans la configuration (no vrrp 1 preempt, « Preempt Mode No » relevé le 2026-10-23) : la cause de ce retour, après coupure puis rétablissement de l’interface underlay du maître, n’est pas établie. 72-perte-switch n’exige donc plus que le plus prioritaire redevienne maître : il vérifie qu’il n’y a qu’un maître, note lequel, et mesure le plus long silence après le retour ;

  • une suppression de VM peut durer 300 s quand l’invité ignore l’arrêt ACPI (#79) : wait_state attend jusqu’à 360 s.

Hypothèses vérifiées en lab, à garder en tête en écrivant un test :

  • systemd-networkd ne réécrit pas un bail renouvelé à l’identique : un renouvellement se vérifie par le DHCPACK dans le journal du serveur (lease_renewed), pas par le fichier de bail ;

  • l’agent n’accepte qu’un seul disque virtio (le disque racine, vda) ; les autres sont des xvdX ;

  • sur Debian 12, ebtables -L (nft) garde les zéros de tête des MAC ;

  • interface_ip est posée en /32 sur le bridge du netns en mode bridge ;

  • depuis le netns d’un hôte, une VM d’un autre hôte ne répond pas : la réponse repart vers la gateway de son propre hôte. Une vérification entre hôtes passe par une VM.

Les VM sont accessibles depuis le netns de leur VPC, sur l’hyperviseur, avec l’utilisateur syonad créé par les métadonnées de two :

test/e2e/labctl.sh ssh "./labctl ssh hv1 'sudo ip netns exec vp-t41 ssh -i /root/.ssh/lab-vm syonad@10.41.1.10'"

Écrire un test#

Un test est un fichier test/e2e/suite/NN-nom.sh, exécuté par run.sh sur le Mac. Il commence par un en-tête, puis envoie des blocs aux nœuds par on <nœud> [VAR=valeur…] <<'NODE'. Chaque bloc est précédé des bibliothèques de test/e2e/lib/ :

  • core.sh : check, known, known_flaky, info, appels à l’API, attente des états ;

  • vm.sh : image Debian compatible two, clé SSH, vm_launch (plusieurs NIC et disques, UEFI, user_data, mot de passe), SSH, bail, métadonnées. La MAC de chaque NIC est fournie à l’API : 52:54:00 suivi des trois derniers octets de l’IP (mac_for_ip), unique dans la suite puisque chaque test a sa plage ; --nic sn=ip=mac en impose une autre ;

  • net.sh : VPC, subnets, MAC anycast, trames brutes, règles ebtables, VRRP ;

  • evpn.sh : VRF, BGP, L3VNI, watchdog ;

  • fixture.sh : nettoyage et assert_clean, appelés par le runner. Le nettoyage couvre les ressources t<NN> de l’API, les netns t<NN>-* et les fichiers t<NN>-* / t<NN>.* de /tmp et /var/tmp/e2e (sauf l’état t<NN>.avant) ; il ne joue que pour un test dont l’en-tête « # hôtes: » est rempli. Un test sans aucune vérification propre, hors fixtures, est en échec.

# fonctionnalité: trafic entre deux VM d'un même subnet sur un hôte, isolation entre VPC
# hôtes: hv1
# tickets: #NN

on hv1 <<'NODE'
KEY=$(vm_key)
check "VPC vp-t99" vpc_create vp-t99 10.99.0.0/16
check "subnet sn-t99" subnet_create sn-t99 vp-t99 9901 10.99.1.0/24
check "VM t99-a" vm_launch t99-a --nic sn-t99=10.99.1.10 --sshkey "${KEY}"
check "VM t99-b" vm_launch t99-b --nic sn-t99=10.99.1.11 --sshkey "${KEY}"
check "t99-a joignable" vm_wait vp-t99 10.99.1.10
check "t99-a joint t99-b" vm_ssh vp-t99 10.99.1.10 'ping -c 2 -W 2 10.99.1.11'
check "VPC vp-t99b" vpc_create vp-t99b 10.99.0.0/16
check "subnet sn-t99b" subnet_create sn-t99b vp-t99b 9902 10.99.2.0/24
check "VM t99-c" vm_launch t99-c --nic sn-t99b=10.99.2.10 --sshkey "${KEY}"
check "t99-c joignable dans son VPC" vm_wait vp-t99b 10.99.2.10
check "t99-a ne joint pas t99-c (autre VPC)" vm_fails vp-t99 10.99.1.10 'ping -c 2 -W 2 10.99.2.10'
NODE

Les règles :

  • une vérification par ligne, avec check : jamais un echo RÉUSSI écrit à la main ;

  • toute vérification négative a son témoin : avant « ne joint pas », une ligne qui prouve que la cible est vivante et que le chemin du test fonctionne ;

  • ``vm_fails`` pour le négatif, jamais ! devant un vm_ssh : un SSH en panne doit échouer, pas passer pour une isolation ;

  • une donnée qui distingue réellement les cas : rien n’empêche deux subnets de porter les mêmes MAC (c’était le cas quand two les dérivait du rang de l’IP) ; comparer des couples MAC/IP, pas des MAC ;

  • les mesures en ``INFO``, les attentes en check : un temps de reconvergence se mesure, il ne se décrète pas ;

  • l’en-tête ``# hôtes:`` liste exactement les hôtes où le test crée des ressources : ce sont ceux que le runner nettoie et compare ;

  • un échec connu se marque known (ou known_flaky) avec son ticket, et le ticket liste le marqueur : jamais un contrôle retiré ou affaibli pour faire passer la suite ;

  • variables vers un nœud : on hv1 NOM=valeur <<'NODE' (valeurs échappées par run.sh) ;

  • bash test/e2e/run_test.sh vérifie le runner, les bibliothèques et la syntaxe de chaque bloc réellement envoyé : à lancer avant toute session.

Note

Un Broken pipe (client_loop: send disconnect) ou une session SSH figée dans un scénario n’est pas forcément un aléa du lab : c’est la signature de ce problème. Ne pas le classer comme test instable ni ajouter un nouvel essai qui le masquerait ; regarder d’abord le cache ARP de la VM (ip neigh show <gateway>) et l’état de la session côté VM.

Sécurité#

Propre à two — celle de l’outil (clé d’API, clés SSH des VM, images) est décrite dans le guide de labctl :

  • labctl et lab-host.sh sont vérifiés contre des sommes épinglées dans test/e2e/labctl.sh, pas contre le SHA256SUMS téléchargé avec eux.

  • Code exécuté sans épinglage par deploy.sh : la bibliothèque shflags est récupérée par curl sur la branche main d’un autre dépôt (H6N/tools) et exécutée par eval, sans vérification d’intégrité — dans le lab comme en production. Les artefacts de la release sont, eux, vérifiés contre SHA256SUMS.

  • Le lab n’a aucune donnée personnelle ni secret de production.
